# Persona and procedural learning

The reader and documentary curator have distinct identities and memories. Their
SOUL files request research rigor, first-principles analysis, practical experiments,
clear explanations for a fifteen-year-old, and attention to differentiation and
constraints. These are behavioral instructions, not measured IQ or qualifications,
nor impersonation of an entrepreneur.

`profiles/reasoning/SKILL.md` is the initial reusable method. Install an independent
copy as `skills/raisonnement-documente/SKILL.md` inside each Hermes profile, then
pin it with the native curator command. Do not symlink the writable skill trees
together. Learned skills and their history remain private and outside this repo.

`profiles/learning.json` is a declarative settings overlay, not a standalone full
configuration. Preserve all existing settings when applying it. Enable the native
`skills` toolset beside the existing memory and bounded MCP tools on each supported
surface. This does not enable terminal, web, arbitrary files, SQL, delegation or
publication. Model routing and reasoning effort stay at their existing values.

Skill creation stays profile-local, external directories and project discovery
are disabled, inline shell is disabled, and agent-created skill scanning is on.
Runtime instructions limit learned methods to Markdown. These controls do not
make the root-owned Hermes process an OS sandbox; the existing non-root MCP
boundaries continue to protect the documentary service.

The post-turn background review uses the main model route, a 48,000 aggregate
input-token budget, no extra tools, and ten-turn memory/skill nudge intervals.
This enables a bounded learning mechanism; it does not promise a review or a new
skill after every answer. The native skills curator is enabled with model-driven
consolidation off. It maintains procedural skills, whereas the Knowledge Forge
documentary curator writes source-linked research proposals.

## Qualify before claiming improvement

1. Back up both profile configurations and instruction files; retain neighboring
   profile hashes. Keep those private artifacts outside Git.
2. Confirm the effective main model, effort, toolsets, and skill roots.
3. In a fresh session, have each profile read the method, solve a synthetic case,
   and create a narrowly scoped Markdown skill through `skill_manage`.
4. Check the actual file and native ledger. In another fresh session, load the
   learned skill and solve a changed case without repeating the stored procedure
   in the request. Assess arithmetic, uncertainty and pedagogical clarity.
5. Verify source counts, neighboring profile hashes and service availability.
   A successful learning receipt proves persistence, not a general intelligence
   gain, domain expertise or freedom from future errors.

Existing conversations may retain old identity and tool schemas. Start a new
conversation to load the updated profile; do not merge profile memories. A native
`/refine` review can be requested for a completed session. Do not claim it ran
unless its returned actions or persisted usage establish that it did.

Hermes' one-shot footprint explicitly discourages skill creation because that run
is ephemeral. Test learning in an interactive/persistent session, then verify
reuse in a separate session; a read-only one-shot can test reuse. When invoking
the CLI from automation, pass `--in` with the profile's instruction directory so
its AGENTS.md is actually loaded. Merely storing `agent.system_prompt` or placing
AGENTS.md in HERMES_HOME is not proof it entered a one-shot system prompt. Check
the persisted prompt for the exact test session. Batch documentary curation stays
separate and is not a claim that every episode autonomously writes a new skill.
